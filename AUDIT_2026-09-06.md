# App audit — 6 September 2026

> Remediation update: the ten confirmed defects below were fixed in the working tree after this audit. Regression coverage now lives in `core/audit-fixes.test.ts`; the full portable suite, lint, production build, isolated populated-library browser smoke test, and macOS native activation test were rerun as part of the fix.

Reviewed commit `34188d3`. The working tree was clean when the audit began. No application code was changed. Findings below are based on code inspection, an isolated browser run, and reproducible service scenarios with generated fonts and the no-op native adapter.

The checkout is not ready to release: the normal build fails, the populated library crashes during rendering, and several recovery paths can alter unrelated or newer font installations.

**1. [P1] A populated font library crashes on render**

[src/App.tsx:2668](/Users/daniel/git/font-butler/src/App.tsx:2668), [src/App.tsx:2447](/Users/daniel/git/font-butler/src/App.tsx:2447)

`LibraryCard` declares an `onSwitch` prop in its type but omits it from parameter destructuring. Both action components reference the unbound variable during rendering. Opening the isolated app with seeded fonts produced a blank page and the exact ReferenceError above; clicking Switch is not required.

Suggested change: destructure the callback, correct the drag helper's event contract (or pass the native event), and remove the unused planner variable. Add a browser smoke test that boots with at least one catalog entry. The existing CI already runs tests, lint, and build; require that workflow to pass before release.

**2. [P1] Startup recovery can delete an unrelated font with the same filename**

[core/journal.ts:125](/Users/daniel/git/font-butler/core/journal.ts:125), [core/journal.ts:351](/Users/daniel/git/font-butler/core/journal.ts:351)

The journal guesses destinations from the source basename, while the installer selects a hashed filename when the basename is occupied. Recovery deletes every guessed destination for an entry that was previously uninstalled, without establishing that the transaction created that file.

Reproduction: install `a/Regular.ttf` as family A; import `b/Regular.ttf` as unrelated family B; prepare B's install journal; simulate restart recovery before any B bytes are written. A's working installed file is deleted.

Suggested change: reserve and record exact destinations before mutation, including whether each existed and who owned it. Recovery must only delete files proven to belong to the interrupted transaction. Cover crashes before the first write and collisions at both destinations.

**3. [P1] Failed mutations discard the journal before recovery is complete**

[core/journal.ts:254](/Users/daniel/git/font-butler/core/journal.ts:254), [core/journal.ts:424](/Users/daniel/git/font-butler/core/journal.ts:424)

`withMutationJournal` completes and deletes the journal in `finally`, including when the mutation fails. Startup recovery also removes its journal and snapshots after a recovery error. This makes transaction recovery unavailable exactly when it is needed.

Reproduction: install version 1, update the source to version 2, then inject a catalog rename failure after the destination copy succeeds. The install rejects; the file contains version 2; the catalog still claims version 1; no incomplete journal remains.

Suggested change: finish a journal only after both bytes and catalog commit, or after verified rollback. Preserve failed journals and snapshots for retry. Keep file rollback material until catalog persistence succeeds, and cover catalog-save and recovery failures explicitly.

**4. [P1] Revision restore can overwrite a different active copy**

[core/service.ts:1696](/Users/daniel/git/font-butler/core/service.ts:1696), [core/service.ts:1708](/Users/daniel/git/font-butler/core/service.ts:1708)

Restore trusts the entry's historical `installedPath` and writes directly without checking current destination ownership or the identity mutex. It also restores a deactivated font into the live font directory, clears `disabledPath`, and leaves the former parked file behind.

Reproduction: install and update copy A; deactivate it; install same-identity copy B from another folder with the same basename. B occupies A's old live path. Restoring A overwrites B's bytes and requests native deactivation of that path, while B's catalog record continues to say installed. A separate test confirms that restoring a parked font strands its previous parked file even without a sibling.

Suggested change: route restore through the same destination reservation, identity preflight, and journal transaction as installation. Restore inactive revisions inside the disabled vault and atomically update the corresponding installation record. Never overwrite a path based solely on its historical association with an asset.

**5. [P1] Concurrent project activation bypasses the identity mutex**

[core/service.ts:1981](/Users/daniel/git/font-butler/core/service.ts:1981), [core/service.ts:2009](/Users/daniel/git/font-butler/core/service.ts:2009)

Project activation invokes private installation and activation helpers without `runCatalogTask`. Separate calls can both pass occupancy checks before either commits. Public HTTP handlers do not add serialization.

Reproduction: create two projects containing different revisions of the same face under distinct filenames; activate both with `Promise.all`. Both operations succeed, and both same-identity files are present and recorded as installed.

Suggested change: put project preflight, project state, owners, file mutations, and final catalog commit inside the shared coordinator. Recheck conflicts within that boundary. Apply the same rule to Undo and project mutation methods that currently invoke private helpers outside it.

**6. [P1] Activating a project silently violates another active project's pin**

[core/service.ts:2006](/Users/daniel/git/font-butler/core/service.ts:2006), [core/projects.ts:121](/Users/daniel/git/font-butler/core/projects.ts:121)

Pin conflicts are checked while editing a pin, but not when activating an already configured project. Restore also lacks a pin check. The project-state helper checks installation status without comparing the installed fingerprint against the member pin.

Reproduction: while both projects are inactive, pin P1 to version 1 and P2 to version 2 of the same asset. Activate P1, then P2. Both report success; P2 replaces the bytes required by P1; `projectState(P1)` still reports active.

Suggested change: validate all active-project requirements before changing any files, reject incompatible activation with the conflicting project name, and derive satisfaction from fingerprint, destination, and activation facts. Do not set `desiredActive` before validating the plan.

**7. [P1] Undo of an old operation can remove a newer installation**

[core/service.ts:1755](/Users/daniel/git/font-butler/core/service.ts:1755), [core/service.ts:1795](/Users/daniel/git/font-butler/core/service.ts:1795)

Undo has no expected-current-revision or operation-generation check. Every historical successful install remains eligible for its original inverse action even after subsequent changes.

Reproduction: install version 1; reinstall version 2; undo the original installation from Activity. Undo reports success and removes version 2's installed file.

Suggested change: persist each operation's before and after state, and compare the current state with the recorded after state under the catalog coordinator. Reject stale Undo without mutation or present a newly computed recovery plan. Include pins and activation owners in those checks.

**8. [P2] Some Undo buttons report success without performing an inverse action**

[core/operations.ts:91](/Users/daniel/git/font-butler/core/operations.ts:91), [core/service.ts:1814](/Users/daniel/git/font-butler/core/service.ts:1814), [core/service.ts:1823](/Users/daniel/git/font-butler/core/service.ts:1823)

Operation completion enables Undo for nearly every successful action, but the dispatcher implements only some of those actions and has no unsupported-action failure branch. It also marks the original operation undone even if inverse items fail.

Reproduction: activate a project, then undo its `activate-project` activity item. Undo reports one success and marks the action undone, but the project remains desired-active and its font stays installed.

Suggested change: use an explicit registry of supported inverse operations and enable Undo only when a complete recovery record exists. Report unsupported actions honestly, retain retryability for failed items, and return actual failed IDs and errors to the renderer.

**9. [P2] Removing members from an active project leaves orphan activation owners**

[core/service.ts:1949](/Users/daniel/git/font-butler/core/service.ts:1949), [core/service.ts:1971](/Users/daniel/git/font-butler/core/service.ts:1971)

Membership editing replaces the member array without reconciling activation owners. Later deactivation and deletion only visit the new member array, so they cannot release removed members.

Reproduction: activate a project containing one font, remove that member, deactivate the project, then delete it. The font remains installed and retains an activation owner referring to the deleted project.

Suggested change: diff old and new members within the catalog transaction; release removed project owners, preserve manual/shared demand, and activate newly required members when appropriate. Clean up existing dangling project-owner references during reconciliation.

**10. [P2] The revision storage budget cannot reclaim normal old revisions**

[core/revisions.ts:69](/Users/daniel/git/font-butler/core/revisions.ts:69), [core/revisions.ts:134](/Users/daniel/git/font-butler/core/revisions.ts:134), [core/service.ts:2119](/Users/daniel/git/font-butler/core/service.ts:2119)

Every stored revision starts with a positive reference count and subsequent stores increment it. `releaseRevision` has no callers. Eviction only considers nonpositive counts, so old blobs remain ineligible after their history is pruned. Additionally, the service's `revisionStorage` method has no normal application caller.

Reproduction: install four successive revisions, prune activity to one operation, and lower the budget to two font files. Even explicitly invoking `revisionStorage()` evicts nothing and remains over budget despite obsolete, unpinned revisions.

Suggested change: compute live references from catalog rollback pointers, retained operation records, pins, and journals, or balance every acquisition and release. Run eviction after retention changes and revision creation; expose usage and explain cases where required recovery data exceeds the budget.

**Suggested implementation order**

1. Fix the render/build blockers and add the populated-library smoke test.
2. Fix destination ownership and journal lifecycle, then run fault-injection and crash tests before enabling the affected restore paths.
3. Serialize project and Undo workflows, enforce pins, and reconcile activation ownership.
4. Implement explicit, state-checked Undo and revision retention.
5. Extend the current CI with these workflow regressions and a separate macOS native acceptance job.

**Further code and product improvements**

- Consolidate `core/types.ts` and `src/lib/types.ts` into a shared API contract. Use a consistent batch result with item outcomes, failed IDs, and errors throughout the UI.
- Split the roughly 3,746-line service into installation transactions, recovery, project ownership, and source automation modules. Extract the roughly 2,989-line App component's orchestration into focused hooks and views after the behavioral fixes have regression coverage.
- Add an error boundary with a recoverable error screen; it should preserve access to diagnostic information when a card fails.
- Make comparison previews resolve immutable captured bytes and metadata together. Current preview URLs label a revision through query parameters while the service still reads mutable source paths for source previews.
- Correct specimen feature toggles: false values are filtered out of `font-feature-settings`, so they cannot explicitly disable default-on features. Encode both `1` and `0`, with defaults reflected in the controls. This was identified by inspection, not browser interaction because of the render crash.
- Profile representative large libraries before optimizing. Synchronous parsing, hashing, and JSON persistence run on the backend thread, which is also Electron's main process in the packaged app. Consider workers and list virtualization based on measurements; no performance benchmark was performed in this audit.
